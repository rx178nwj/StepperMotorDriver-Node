# CAN インタフェース仕様書（上位機器・マスタ開発者向け）

| 項目 | 内容 |
|------|------|
| 対象 | NEMA23 ステッピングモータードライバ（STM32、ファームウェア 0.4） |
| 目的 | CAN バス上の上位機器（PLC・マイコン・PC＋CAN アダプタ等）が、最大 8 台の本機を制御・監視できるようにする |
| 版 | 0.1（2026-10-20） |
| 正 | `requirements.md` 3.8 節と実装（`firmware/App/Src/comm.c`、`app.c`）。食い違いは実装を正とし、本書を直す |

## 1. 全体像

```
上位機器（マスタ）
   │  CAN バス 500 kbit/s（CANH / CANL / GND）  両端のみ 120Ω 終端
   ├── 本機 ID=0
   ├── 本機 ID=1
   └── …（最大 8 台、ID 0〜7）
```

- マスタが要求を送り、本機が応答する**マスタ・スレーブ方式**。1 要求に最大 1 応答。
- 本機から自発的に送るのは**異常通知**（FAULT 遷移時の 1 回）だけ。起動通知・周期送信はない。
- 操作はすべてレジスタの読み書きと COMMAND（レジスタ 0x50）で行う。

## 2. 物理層

| 項目 | 値 |
|------|----|
| プロトコル | CAN 2.0A（クラシック CAN）。**CAN FD は使えない**。標準 11 bit ID のみ（拡張 ID・リモートフレームは受信しない） |
| ビットレート | **500 kbit/s 固定**（`requirements.md` FR-COM-02。変更はファームの定数を書き換えて再ビルド）。サンプルポイント 87.5%（16 tq、SJW=1） |
| コントローラ | STM32 bxCAN（CAN1）。PB8=RX、PB9=TX |
| トランシーバ | TJA1441AT。常にノーマルモード（S=Low）。ファームからサイレントへ切り替えない |
| 電源 | 本機は CAN バスに 5 V を出さない |
| 終端 | 基板上 120Ω を DIP スイッチ SW2 の 4 極目（CAN_TERM）で ON/OFF。**バス両端の 2 台だけ ON**（ファームからは状態を読めない） |
| 保護 | TVS（PEC3824C2A-AU）実装 |

### 2.1 コネクタ（J1 / J2）

JST PH 3 ピン（B3B-PH-K-S）。J1 と J2 は同一ネットの並列で、数珠つなぎ用（どちらを入力にしてもよい）。

| ピン | 信号 |
|------|------|
| 1 | CANH |
| 2 | CANL |
| 3 | GND |

### 2.2 DIP スイッチ SW2（ID と終端）

| 極 | 機能 |
|----|------|
| 1 | ADDR0（bit0、ON=1） |
| 2 | ADDR1（bit1、ON=1） |
| 3 | ADDR2（bit2、ON=1） |
| 4 | CAN_TERM（ON=終端 120Ω 接続） |

ID = ADDR0 + 2×ADDR1 + 4×ADDR2（0〜7）。

**ID は起動時に 1 回だけ読む**。実行中に DIP を変えても反映されない（受信フィルタも起動時の ID で作られる）。変更後は電源を入れ直す。

### 2.3 配線・運用上の注意

- バスは両端のみ終端（合成 60Ω）。終端が 0 個または 3 個以上だと通信が不安定になる。
- **ID が同じ本機を 2 台つながない**。重複検出はなく、同じ応答 ID で同時に送信してバスエラーになる。
- 本機が 1 台だけで、かつ他に ACK を返す機器がない（上位機器が未接続・停止など）と、送信が再送を繰り返してバスが詰まり、応答と異常通知が破棄される。必ず ACK を返せる相手を接続した状態で使う。

## 3. CAN ID の割り当て

基板ID を `ID`（0〜7）とする。

| CAN ID | 方向 | 用途 | 優先度（調停） |
|--------|------|------|---------------|
| 0x000 | マスタ→全台 | ブロードキャスト（応答なし） | 最高 |
| 0x080 + ID | 本機→マスタ | 異常通知 | ↑ |
| 0x100 + ID | マスタ→本機 | 要求（書き込み・読み出し） | ↓ |
| 0x180 + ID | 本機→マスタ | 応答 | 低 |

- 本機が受信するのは **0x000 と 0x100+自局 ID のみ**。他局宛て（0x100+他の ID）や、その他の ID はハードウェアフィルタで捨てられ、ACK 以外の反応はない。
- ID 0 は 0x000 とは衝突しない（0x100/0x180/0x080 を使う）。
- ID 0x200 以上は使われていない。上位側の既存システムと ID が衝突しないかは、導入先で確認する（11章 1.）。

## 4. フレーム仕様

すべて標準 ID・データフレーム、データ長 DLC は 0〜8。多バイト値は**リトルエンディアン**。

### 4.1 書き込み要求 / 応答

```
要求  CAN_ID = 0x100+ID, DLC = 3〜8
      DATA = [0x01][REG][VALUE 1〜6 バイト]

応答  CAN_ID = 0x180+ID, DLC = 3
      DATA = [0x81][REG][CMD_RESULT]
```

- REG は書き込みを始めるレジスタの先頭アドレス。VALUE はそこから連続するレジスタの値を昇順に並べたもの。
- 例: RUN_CURRENT（0x20、u16）に 1500 mA(0x05DC) → `01 20 DC 05`（DLC 4）。

### 4.2 読み出し要求 / 応答

```
要求  CAN_ID = 0x100+ID, DLC = 3
      DATA = [0x02][REG][LEN]          LEN = 1〜6

応答  CAN_ID = 0x180+ID, DLC = 2+LEN
      DATA = [0x82][REG][DATA LEN バイト]
```

- 応答は要求を処理した時点のスナップショット（読み出し中に値が変わっても一貫した値）。
- 例: STATE・FAULT（0x04 から 2 バイト）→ 要求 `02 04 02`、応答 `82 04 <STATE> <FAULT>`。

### 4.3 不正要求の応答

```
CAN_ID = 0x180+ID, DLC = 3, DATA = [0xFF][REG][0x02]
```

次の場合に返る。

| 条件 | REG の値 |
|------|----------|
| 未定義の OP（先頭バイトが 0x01・0x02 以外） | 要求の REG |
| 書き込みで DLC が 3 未満または 9 以上 | 同上 |
| 読み出しで DLC が 3 でない | 同上 |
| 読み出しの LEN が 0 または 7 以上 | 同上 |
| DLC が 0 または 1（REG が存在しない） | 0 |

### 4.4 ブロードキャスト

```
CAN_ID = 0x000, DLC = 1, DATA = [COMMAND]
```

- COMMAND が **2（DISABLE）・3（STOP）・4（ESTOP）** のときだけ全台が実行する。それ以外の値や DLC≠1 は**無視される**（応答・エラーもない）。
- 応答はない。実行結果は各台のレジスタで確認する。
- ブロードキャストは CMD_RESULT（レジスタ 0x07）を更新せず、通信タイムアウトの計時にも数えられない。
- 用途は緊急停止（全台一斉停止）。ENABLE や移動指令はブロードキャストでは出せない。

### 4.5 異常通知

```
CAN_ID = 0x080+ID, DLC = 2, DATA = [STATE][FAULT]
```

- STATE が **FAULT に遷移したとき 1 回だけ**送信する。STATE=3 が入る。FAULT は故障ビット（`usb_interface.md` 8.4 章）。
- 周期送信ではない。**NO_VM・DISABLED・ENABLED への遷移、FAULT 中の追加故障ビット、CLEAR_FAULT による解除では送らない**。状態の変化は定期的な読み出しで把握すること。
- バスに送れない状況（送信バッファ満杯・バスオフ等）では、1 件だけ保留して再試行する。保留中にさらに通知が発生すると古い方が破棄される。取りこぼしがありうるため、通知は**きっかけ**として扱い、正は常にレジスタ読み出しとする。
- 通知を受けたら STATE と FAULT を読み、原因を除いたのち COMMAND=5（CLEAR_FAULT）で解除する。

## 5. レジスタ・COMMAND

レジスタマップ（アドレス・型・範囲・既定・保存）、STATE、FAULT、CMD_RESULT、COMMAND 1〜12 の動作と受付条件は、[usb_interface.md](usb_interface.md) の **8.3〜8.6 章**を参照する。CAN と USB で同一である。

本書で CAN 固有の扱いだけ補足する。

### 5.1 書き込み時の動作

- 複数レジスタを 1 フレームで書くと、**含まれるレジスタが昇順に 1 つずつ反映**される。途中で拒否されても、すでに反映されたものは取り消されない（ロールバックなし）。
- 32 bit レジスタは 4 バイトすべて、16 bit レジスタは 2 バイトすべてがフレームに入っているときだけ反映される。一部だけ入っているバイトは反映されず、その場合 CMD_RESULT は 2（INVALID）になる。
- 書き込み専用・未定義アドレスへの書き込みは反映されず、CMD_RESULT=2。
- CMD_RESULT（応答の第 3 バイト）は、要求に含まれる全レジスタのうち**最後の非 OK の値**（すべて OK なら 0）。
- 設定値の範囲外は丸めずに INVALID（2）。状態による拒否は REJECTED（1）。
- **推奨: 設定の書き込みは 1 フレーム 1 レジスタ**にする（結果の解釈が単純）。
- 以上は `requirements.md` FR-COM-08 の記述（部分書き込みは一切反映しない）より緩い。実装を正とする。

### 5.2 読み出し時の動作

- マップ内の未使用領域（0x1F、書き込み専用の 0x40〜0x53 など）は 0x00 が返る。マップ外（0x60 以上）は 0xFF。
- 読み出しでは CMD_RESULT（0x07）は変わらない。書き込み応答のたびに更新される。
- 1 回の読み出しは最大 6 バイト。32 bit 値は 4 バイトなので、隣り合うレジスタを 1 回にまとめて読む（例: STATE(0x04)＋FAULT(0x05) ＝2 バイト）。0x00〜0x5F 全体は約 16 回。

### 5.3 CAN でできないこと

次は USB でのみ可能。

- ENTER_BOOTLOADER（ファームウェア書き換えモードへの移行）。COMMAND に 0x50 は無く、INVALID になる。
- 通信統計（comm_stats、`usb_interface.md` は USB の名前表経由で読める）、メモリ読み出し、名前表。
- CONNECT などのセッション管理。CAN にはセッションがなく、いつでも要求できる。

## 6. タイミング

| 項目 | 値 |
|------|----|
| 応答時間 | 要求受信から応答のバス送出開始まで **2 ms 以内**（FR-COM-11）。実装上は受信割り込み後、最大 1 ms 周期の処理でバスに載せる。バス上の伝送時間（8 バイトで約 0.25 ms @500 kbit/s）は別途 |
| 例外 | 設定の保存（SAVE_SETTINGS）中は Flash 消去で CPU が最大約 25 ms 止まる。この間は応答が遅れ、受信も取りこぼしうる。マスタは SAVE 後に**十分な待ち時間（推奨 100 ms 以上）**を置く |
| 要求の間隔 | 同一の本機への要求は、応答を受け取ってから次を送る（1 要求ずつ）。本機の受信キューは 16 件だが、連続投入は避ける |
| タイムアウト | マスタ側で、応答待ちは 10 ms 以上（推奨 20〜50 ms）を設定。応答がなければ読み出しのみ再送してよい |
| 起動 | 電源投入後、起動処理が終わると要求に応答する。起動通知は無い。NO_VM（モータ電源なし）でも CAN は応答する（ENABLE は REJECTED） |

### 6.1 再送の方針（マスタ側）

- **読み出し**: 応答がなければ再送してよい（最大 3 回程度）。
- **書き込み・COMMAND**: 本機が実行済みで応答だけが失われた可能性があるため、**盲目的に再送しない**。移動指令（MOVE_REL）の再送は二重移動になる。応答がなければ状態レジスタを読んで確認してから判断する。冪等な指令（MOVE_ABS、RUN_SPEED、STOP など）は再送してよい。
- **ブロードキャスト**: 応答がないため、効果の確認は各台の STATE・SPEED の読み出しで行う。確実に止めたいときは繰り返し送ってよい（STOP/ESTOP/DISABLE は冪等）。

### 6.2 送信順序

本機の送信はメールボックスの ID が小さい順に出る。異常通知（0x080+ID）は応答（0x180+ID）より優先してバスに出る。

## 7. 通信タイムアウト（COMM_TIMEOUT、レジスタ 0x26）

上位機器の停止・断線時に本機を自動で止める機能。

- 既定は 0（無効）。ms 単位の値を書くと有効になる。
- **「最後の要求」として数えられるのは、自局宛て 0x100+ID のフレームを受信した時刻**。読み出し・書き込み・不正要求を問わない。ブロードキャスト（0x000）と他局宛てのフレームは数えない。**USB の CAN_REQUEST で渡した要求は数えない**（USB のデバッグ操作でタイムアウトが延びないようにするため）。
- 最後の要求から指定時間を超えると、**減速停止**し、原点復帰を中止する（FAULT にはならず、STATE は ENABLED のまま。異常通知も送らない）。
- ジョグ（前面スイッチ）操作中は適用されない。ENABLED の間だけ判定される。
- したがってマスタは、タイムアウト値の 1/3 以下の周期で**何らかの要求（状態の読み出しで可）を各台に送り続ける**。
- 起動直後は無効（既定 0）。設定を保存しておけば次回起動から有効。

## 8. 障害時の挙動

| 事象 | 本機の動作 |
|------|-----------|
| 受信キュー（16 件）あふれ | 新しいフレームを捨てる（統計 rx_dropped） |
| 送信メールボックス満杯 | 応答を破棄（統計 tx_dropped）。再試行しない |
| エラーパッシブ・バスオフ | 自動で復帰（バスオフからは CAN 規格どおり自動復帰）。この間、前面 LED_COMM が 2 Hz で点滅 |
| 自動再送 | 有効（ACK が付くまで再送を続ける） |
| CAN の初期化失敗 | 外部に何も送らない（LED/統計で確認、USB から読める） |
| 本機のリセット（IWDG・電源断） | CAN はリセットされ、起動後に ID を読み直す。モータは停止・非励磁（STATE=NO_VM または DISABLED）に戻る。マスタは STATE を読んで復帰処理を行う |

統計（`comm_stats`）は USB の名前表（`comm_stats`）でのみ読める。項目: rx_frames、rx_dropped、tx_frames、tx_dropped、err_events、err_passive、err_busoff、err_rx_overrun、err_last_code。電源再投入まで累積し、クリアの手段はない。

診断情報（`comm_diag`）も名前表で読める。TEC/REC（と起動後の最大値）、LEC 別のエラー回数（Stuff/Form/ACK/Bit/CRC）、初期化の段階（失敗した HAL 関数）、直近に受信したフレームが分かる。TEC/REC/LEC は 1 ms ごとのサンプリングなので、回数は下限値。

## 9. マスタ実装ガイド

### 9.1 推奨層構成

| 層 | 責務 |
|----|------|
| CAN ドライバ | アダプタ（SocketCAN、PCAN、Kvaser 等）の送受信。標準 ID、500 kbit/s、**自動再送は有効のまま** |
| プロトコル | `write_reg(id, reg, bytes) -> result`、`read_reg(id, reg, len) -> bytes`、`broadcast(cmd)`。要求→応答の対応付けとタイムアウト、不正応答（0xFF）の検出 |
| デバイス | 型変換（u16/i32 等）、状態判定、COMMAND ラッパ |
| アプリ | シナリオ・UI |

- 受信は専用スレッド（または非同期）で行い、0x180+ID の応答は待機中の要求へ、0x080+ID の異常通知はイベントとして別配送する。
- 応答の対応付け: CAN には通し番号がないため、**応答の CAN ID（0x180+ID）と第 1 バイト（0x81/0x82/0xFF）・REG が要求と一致するもの**を採用する。同一本機への要求は 1 つずつ直列に行う。複数台へは並行して要求してよい（応答 ID が台ごとに異なる）。

### 9.2 典型シーケンス（ID=3）

```
起動: STATE を読む (02 04 01)
設定: COMM_TIMEOUT 等を書く → COMMAND=7 で保存 → 100 ms 待つ
運転:
  STATE==DISABLED なら COMMAND=ENABLE (01 50 01)
  STATE==ENABLED を確認
  MOVE_ABS を書く (01 40 <i32 LE>)
  周期（20〜100 ms）で STATE/STATUS/POSITION を読む  ← 生存通知を兼ねる
  STATUS bit7（目標到達）または POSITION で完了を判定
停止: COMMAND=STOP (01 50 03) または DISABLE (01 50 02)
異常: 0x083 の通知 or STATE==FAULT → FAULT を読む → 原因除去 → CLEAR_FAULT (01 50 05)
緊急: 0x000 に 03 または 04 を送る（全台）
```

### 9.3 フレーム例（ID=3、すべて 16 進）

| 目的 | CAN_ID | DLC | DATA | 期待する応答（CAN_ID=0x183） |
|------|--------|-----|------|------------------------------|
| ENABLE | 103 | 3 | `01 50 01` | `81 50 00`（DISABLED のとき）、他は `81 50 01` |
| 絶対 3200 step へ移動（0x0C80） | 103 | 6 | `01 40 80 0C 00 00` | `81 40 00` |
| 速度 1600 step/s で連続回転（0x0640） | 103 | 6 | `01 48 40 06 00 00` | `81 48 00` |
| 減速停止 | 103 | 3 | `01 50 03` | `81 50 00` |
| STATE・FAULT を読む | 103 | 3 | `02 04 02` | `82 04 <STATE> <FAULT>` |
| POSITION を読む | 103 | 3 | `02 08 04` | `82 08 <i32 LE>` |
| RUN_CURRENT を 1500 mA に | 103 | 4 | `01 20 DC 05` | `81 20 00` |
| 設定を保存 | 103 | 3 | `01 50 07` | `81 50 00`（保存完了まで 100 ms 以上待つ） |
| 全台 STOP | 000 | 1 | `03` | なし |
| 全台 ESTOP | 000 | 1 | `04` | なし |
| 異常通知（受信） | 083 | 2 | `03 <FAULT>` | — |
| 不正要求（未定義 OP=0x05） | 103 | 3 | `05 04 01` | `FF 04 02` |

## 10. 受け入れ試験（マスタ実装の確認項目）

| # | 項目 | 期待結果 |
|---|------|----------|
| 1 | 4.2 章: 読み出し `02 00 01`（DEVICE_ID） | 応答 `82 00 A3` |
| 2 | BOARD_ID（0x03）を読む | DIP で設定した ID と一致 |
| 3 | DLC=2 の書き込み、LEN=0・7 の読み出し | `FF <REG> 02` |
| 4 | 他局宛て 0x100+X へ送信 | 応答なし（フィルタで破棄） |
| 5 | NO_VM で ENABLE | 応答 CMD_RESULT=1（REJECTED） |
| 6 | RUN_CURRENT に範囲外（100 mA）を書く | CMD_RESULT=2、値は変わらない |
| 7 | 32 bit レジスタを 2 バイトだけ書く | CMD_RESULT=2、値は変わらない |
| 8 | ブロードキャスト STOP（`03`）を複数台に送る | 全台が減速停止、応答なし |
| 9 | ブロードキャストに 0x01（ENABLE）を送る | 何も起きない（無視） |
| 10 | COMM_TIMEOUT=200 ms を設定し運転中に要求を止める | 約 200 ms 後に減速停止、STATE は ENABLED のまま |
| 11 | 上記で 0x000 の STOP だけを送り続ける | タイムアウトは延長されない（ブロードキャストは対象外） |
| 12 | 運転中に FAULT 要因（過熱・VM 低下等）を発生 | 0x080+ID が 1 回届き、STATE=3 |
| 13 | CLEAR_FAULT | 要因除去後に STATE が DISABLED（または NO_VM）へ |
| 14 | 設定変更→保存→電源再投入 | 設定値が保持される |
| 15 | 2 台以上接続し、それぞれ別 ID に要求 | 各台が自 ID の 0x180+ID で応答 |

## 11. 既知の仕様上の注意・未規定事項

1. **ビットレート・ID 割り当て・終端方式は、要求仕様の暫定値（U-1〜U-3）を確定値として本書に採用した**: 500 kbit/s（FR-COM-02）、ID 割り当て 0x000/0x080+ID/0x100+ID/0x180+ID（FR-COM-03）、DIP 4 極目＋120Ω をバス両端の 2 台だけ ON（H-6）。要求仕様側では U-1〜U-3 が「暫定」のままなので、これらを変える場合は要求仕様と本書を同時に更新する。上位側の既存システムとの ID 衝突の有無（U-2）は、導入先で確認する。
2. **複数レジスタ書き込みの部分反映**: 要求仕様（FR-COM-08）は「反映しない」だが、実装は完全に含まれるレジスタを個別に反映する（5.1 章）。実装を正としているため、どちらに揃えるかは仕様側の判断が必要。
3. **Flash 消去中の受信**: 消去中は割り込みも止まる可能性があり、受信フレームを取りこぼす恐れがある（推測、実機で未確認）。SAVE 実行時は他の要求を止める。
4. **バスオフ中に保留された異常通知**は、復帰後に送られる可能性がある（推測）。
5. **USB との同時操作**は排他していない（U-9）。同時には使わない。
6. **ACK 試験**: フィルタ外のフレームへの ACK の挙動は未確認（推測: ハードウェアは受信を確認すれば ACK するため、フィルタ外でも ACK は返ると考えられる。CAN 仕様上、ACK はフィルタと無関係）。
7. 回路図資料の一部に旧記述（3 極 SW4 の表記）が残る。**現行は SW2（KHS42E、4 極）**。
8. TJA1441AT の VIO 側仕様・TVS のピン配置はデータシート照合が未済。

## 付録 B. Python（python-can）での最小例

```python
import can, struct

bus = can.Bus(interface="socketcan", channel="can0", bitrate=500000)
ID = 3

def request(data: bytes, timeout=0.05):
    bus.send(can.Message(arbitration_id=0x100 + ID, data=data, is_extended_id=False))
    while True:
        m = bus.recv(timeout)
        if m is None:
            raise TimeoutError
        if m.arbitration_id == 0x180 + ID:
            return bytes(m.data)
        # 0x080+ID は異常通知。ここで別途処理する

def read_reg(reg, n):
    r = request(bytes([0x02, reg, n]))
    if r[0] == 0xFF:
        raise ValueError("invalid request")
    return r[2:]

def write_reg(reg, value: bytes):
    r = request(bytes([0x01, reg]) + value)
    return r[2]            # CMD_RESULT: 0=OK 1=REJECTED 2=INVALID 3=FAILED

assert read_reg(0x00, 1) == b"\xA3"                 # DEVICE_ID
write_reg(0x50, bytes([1]))                          # ENABLE
write_reg(0x40, struct.pack("<i", 3200))             # MOVE_ABS
```
